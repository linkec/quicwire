# 设计与实施顺序

更新日期：2026-10-02。当前阶段：需求细化。工程骨架已存在，功能开发尚未开始。

用户要求先完成全部设计，再开发。下面各阶段有明确依赖，不能用“先写原型再想清楚需求”跳过设计。

## D1. 确定产品需求

- 确认主要用途、首版交付平台、HTTP/3 要求、地址族与运行环境。
- 确定 peer、session、路径、带宽和系统配置的用户可见行为。
- 为首版需求分配验收场景，确定量化目标及排除范围。

产出：requirements.md、design-review.md 决策记录及 acceptance.md 的目标条件。

通过条件：产品范围经用户确认，首版不存在未决的功能边界。

## D2. 完成技术设计

按 design-review.md 中的交付表完成：

1. 系统角色、信任边界、配置与部署模型。
2. 密钥与认证、完整握手、路径绑定、轮替和撤销。
3. 线上格式、协商规则、版本兼容、错误码、长度与资源限制。
4. session/path 状态机及所有失败、超时、恢复行为。
5. 数据封装、队列、去重、MTU 与地址族处理。
6. 选路、控制一致性、拥塞控制与带宽预算。
7. 平台接口、路由、NAT、DNS、配置生命周期与日志。
8. 带明确预期结果的验收计划、资源预算和测量方法。

允许查阅标准、阅读库源码、分析现有测量数据；当前阶段不编写原型。需要运行时验证的假设列入证据清单，提前确定验证方式、失败条件与设计回退方案。

通过条件：字段、状态、默认值、上限、异常路径及验收结果都可据文档独立实现；库能力缺口已明确处理方案。

## D3. 评审与设计冻结

- 逐条核对需求、设计和验收的对应关系。
- 审查身份冒用、重放、错误路由、消息乱序、资源耗尽和系统配置回滚。
- 列出每个数值默认值的理由及可调整范围。
- 关闭全部阻塞项，并向用户提供具体设计版本及变更摘要。
- 用户确认完整设计后记录冻结版本，再进入开发。

当前没有任何设计冻结记录，也没有开始功能开发的授权。

## I1. 按冻结设计实现单路径

仅在 D3 完成后开始。完成身份认证、TUN 与单路径 DATAGRAM 数据面，执行对应验收场景。

## I2. 按冻结设计实现多路径

完成路径绑定、复制去重、独立队列、控制一致性与故障恢复。

## I3. 性能与平台验收

依据已冻结的门槛验证资源开销、实际线路和目标平台。验证失败时回到设计评审，不能静默降低验收标准。

## I4. 发布

完成安装、配置、升级、诊断和许可决策后发布首个可用版本。
