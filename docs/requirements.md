# quicwire 需求

更新日期：2026-10-02。状态：需求细化稿，尚未冻结；功能开发须等待全部设计评审完成。

本轮先确定需求与所有设计细节，再开始开发。本文中的既有架构方向继续作为讨论基线；新增建议和未决选项见 [设计决策](design-review.md)，不得将未确认建议当成已经批准的产品范围。

## 已确定的方向

1. 独立项目，语言使用 Rust，QUIC 库使用 Quinn，异步运行时使用 Tokio。
2. 以本地公私钥及预配置 peer 公钥建立身份，不依赖账号、认证 API 或数据库。
3. 多接入、单核心：客户端同时通过不同边缘连接同一核心。
4. 每条路径是一条独立 QUIC 连接，在应用层绑定为同一 session。
5. 上下行 IP 包都能多发，接收端去重；控制链负责路径绑定、选路和多发份数。
6. 保留标准 QUIC 传输；HTTP/3 网站外观与 MASQUE CONNECT-IP 封装需要单独验证。

## 目标与范围

减少单一路径随机丢包、拥塞和故障造成的业务中断。路径应通过不同 ISP、不同线路或不同接入网络建立；仅改变端口不能证明路径独立。

本期不做带宽聚合，不把内层 IP 数据放入可靠 QUIC stream，不以标准 Multipath QUIC 作为首版依赖。可靠 stream 可以承载控制消息，但控制状态需要跨连接同步。

首版平台与用途待确认。当前建议先交付 Linux 客户端与核心，同时在设计中考虑 Android、iOS、Windows 的 TUN、路由、权限、休眠与换网边界。是否将 macOS 列为正式交付平台也需确认。此建议不构成开发授权；原型也须在设计冻结后开始。

## 术语

| 名称 | 定义 |
| --- | --- |
| Peer | 由公钥识别的对端及其本地授权配置 |
| 客户端 | 接入 TUN，并经多条路径连接核心的程序 |
| 边缘 | UDP 转发节点，不终结 QUIC 连接 |
| 核心 | 终结 QUIC、认证 peer、去重并转发流量的服务器 |
| 路径 | 一条客户端 socket 经边缘到核心端点的 QUIC 连接 |
| Session | 已认证 peer 的一次逻辑隧道会话，包含多条路径 |
| K | 同一个内层包发送的副本数量 |
| 发送集合 | 某方向用于发送副本的路径集合，带 epoch 版本号 |
| 控制链 | 跨可用连接传递认证、绑定、测量和调度信息的逻辑通道 |

## 连接流程草案

1. 两端本地生成密钥，预先配置对端公钥。核心按 peer 配置允许的内层地址、路由、速率和多发上限。
2. 客户端经一条边缘路径建立 QUIC 连接，并完成双向身份验证。私钥持有证明应绑定对端身份、本次握手和连接；具体 TLS 身份绑定与密钥类型待协议规格确定。
3. 核心建立 session，通过加密控制链下发会话绑定材料及该 peer 的地址与路由。
4. 客户端经其他边缘并行建立连接，每条连接验证核心身份后，在 1-RTT 完成后请求绑定已有 session。
5. BIND 证明绑定 session、path_id、双方身份与本连接 TLS exporter；会话绑定材料只在本次 session 内有效。编码、标签、密钥派生及重放防护需在规格阶段审查。
6. 两端确认初始 SET 后传输数据，持续交换 REPORT 与 SET；新路径重复认证及绑定，失败路径摘除。

公私钥配置方式参考 WireGuard，不表示复用其握手或 X25519 密钥格式。首次认证与路径绑定不得使用可重放的 0-RTT 数据。

## 必须明确的运行行为

以下内容是需求细化稿的基础约束，须纳入完整设计评审。

### 身份与权限

- 一个 peer 身份不等于一个网络地址：外层 IP、端口、NAT 重绑定不能替代公钥认证。
- 每条新增路径都必须验证核心身份，并证明其属于已授权的 peer/session；知道 session ID 不能取得绑定权限。
- 地址下发不等于转发授权。核心必须校验内层源地址和目的路由，拒绝冒用其他 peer 地址。
- 撤销本地 peer 配置生效后，禁止新绑定并终止其现有 session；轮替与撤销是两种操作，分别设计。
- 同一公钥的并发设备/进程策略、连接数上限、重复地址与前缀冲突策略必须明确。

### Session 与故障

- 单路径失败不能导致其他健康路径重建，控制消息应能通过存活路径继续交互。
- 旧连接迟到的数据和控制消息不能污染新 session；重连后不能无条件沿用旧序号状态。
- 全部路径失效时必须暴露断连状态，停止无界缓存。会话保留时长、有限缓存或直接丢弃、恢复方式需确定。
- 核心进程重启可能丢失 session 和 NAT 状态，不承诺现有业务连接继续存活；客户端应能重新认证建立隧道。
- 不把“peer 仍配置在本机”“TUN 仍然 up”或“最近握手过”作为路径健康的充分证据。

### 多发、队列与去重

- 同一内层包的各路径副本共用同一个方向序号。第一份有效包立即交付，不等待其他副本或更早序号。
- 正确性定义为每个可接受序号最多交付一次；所有副本丢失仍可能造成内层丢包。
- 默认不对内层数据实施应用层重传，控制消息具有确认与重试机制。
- 去重窗口大小、窗口外旧包、极端乱序、重复副本、序号耗尽及重启后的处理都须明确。
- 应用队列、QUIC 内部队列和接收队列均有预算。API 接受一个包不代表它已上网，也不保证对端应用已经收到。
- 同一 peer 的重复加密副本和相关控制开销都占用外层带宽预算；具体限速统计口径须可验证。
- 实际可发送的健康路径少于 K 时，必须报告实际副本数及降级原因；不得向一条路径复制多份来冒充路径冗余。

### 选路与控制

- 上下行可以选择不同集合和 K，核心返回实际接受的配置，双方不能各自假定 SET 已生效。
- SET 的作用方向、发起者、版本、应用时机、确认语义和超时回退须逐项定义。
- 控制消息需要防重复执行、防旧版本覆盖，并明确同一版本不同内容的处理。
- 初次生效、正常切换、故障紧急摘除和恢复加入使用明确的状态转换；控制消息丢失不能使状态永久分歧。
- 仅有多端口不代表物理路径独立，路径归属与策略需要可观测。

### MTU、路由与系统集成

- 分别定义内层 IPv4/IPv6 与外层 IPv4/IPv6 的支持范围，不能由“支持 IP”推断全部组合已支持。
- QUIC DATAGRAM 自身不分片。若目标内层 MTU 无法装入外层载荷，须决定应用分片、可用路径约束或其他完整策略。
- IPv6 内层最小链路 MTU、隧道封装开销与 PMTUD 初始状态必须共同考虑，不能简单将内层 MTU 一律降到 1200。
- 外层连接必须绕过隧道路由，避免递归。默认路由、DNS、NAT 和防火墙是否由程序管理需确认。
- 所有系统配置修改都要有可检查的计划、失败回滚和停止时的清理行为；不能删除用户原有规则。

### 配置与可观测性

- 配置解析、重复键/未知字段、peer 冲突、热更新与重启字段必须有确定规则。
- 无效配置不能替换当前有效配置。私钥及完整会话绑定秘密不得进入日志。
- 区分应用队列丢弃、QUIC 传输层丢包估计、接收端序号缺口与去重丢弃；不能将库未提供的信息报告成精确实测值。
- 日志应能定位 peer、session、path 和失败阶段；不默认记录用户数据包内容。

## 验收边界

- **可靠性**：K ≥ 2，且至少一条已绑定健康路径有足够容量时，单路径故障不应重置逻辑 session；在受控无额外丢包场景验证故障不引入丢包。多路径本身不保证任何网络条件下零丢包。
- **切换**：发送集合切换不能因软件状态更新出现空集合或发送空窗。
- **隔离**：阻塞或填满一条路径队列时，其他路径继续发送，内存保持有界。
- **安全**：拒绝未知公钥、重放认证及跨连接挪用 BIND；撤销 peer 时关闭其已有 session 并拒绝新连接。
- **MTU**：保守配置 TUN MTU，并覆盖 IPv4、IPv6 和路径 MTU 变化；不得把超大包无声丢弃作为完成状态。
- **性能**：量测 K=1/2/3 的 CPU、每秒包数、有效吞吐、P99 延迟、峰值内存；目标硬件、负载、数值门槛和测量方法须在开发前确定；开发后实测验证，修改门槛须重新评审。
- **跨平台**：各目标平台验证 TUN 收发、休眠恢复、网络切换和内存使用。

## 技术边界与待决事项

- [ ] 密钥类型、存储格式、TLS 身份绑定、轮替及撤销协议。
- [ ] 控制消息格式、BIND 证明、SET/epoch 语义、session 超时与重连行为。
- [ ] 采用原生 QUIC 应用协议还是 HTTP/3 + MASQUE CONNECT-IP；后者需要补齐 Rust 集成。
- [ ] DATAGRAM 包头格式；若采用 CONNECT-IP，按扩展规则明确 context 与序号封装。
- [ ] 边缘采用 DNAT+SNAT 或带来源信息的 relay；双向路由与源地址可见性需验证。
- [ ] 拥塞控制基线及总发送速率限制，避免多路径共享瓶颈被重复压满。
- [ ] 默认 K、队列字节上限、副本有效期、去重窗口和健康检测参数。
- [ ] IPv4/IPv6 地址、TUN MTU、ICMP、路由和 NAT 方案。
- [ ] SNI、ALPN 及普通 HTTP/3 服务共存方式；标准 QUIC 外观不等于不可识别。
- [ ] 首版产品场景、交付平台、并发 peer 数及目标硬件。
- [ ] 量化验收门槛、参考负载和目标设备资源预算。
